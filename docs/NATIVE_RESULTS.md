# 首个原生版本验证

本报告保留加入托盘前的历史基线，产物大小、功能范围和实测数值均对应当时版本。最新托盘、亮/暗主题与优化结果见 [TRAY_THEME_RESULTS.md](TRAY_THEME_RESULTS.md)。

2026-10-03，独立 PicoRun 的首个无图标版本已可运行。原生窗口、真实应用发现、热键、单实例、快捷方式启动和可恢复缓存已实现。低内存目标尚未全部达到：普通搜索状态较小，但首次 Shell 启动有明显内存峰值，需要继续优化。

## 构建与运行

- 起点：本地 main 初始提交 `b99a82d`，没有导入 ALTRun/WindMenu 代码。
- 产物：`D:\Workspace\PicoRun\target\release\picorun.exe`，619,008 字节。这是磁盘大小，不是内存。
- SHA256：`1091F2D534BA04C693550B66FD06E3A847C710FE6F5AB22053848AB9ADD9F22A`。
- Rust 1.95.0、`x86_64-pc-windows-msvc`；opt-level=3、fat LTO、codegen-units=1、panic=abort、strip、静态 CRT；`cargo build --release --offline`。没有第三方 Rust crate。
- 默认运行显示窗口；Alt+Space 呼出/隐藏，↑↓ 选择，Enter 打开，Esc/失焦隐藏，F5 刷新，Ctrl+Q 退出。`--hidden` 隐藏启动，`--hotkey Ctrl+Alt+P` 换热键。
- 默认热键占用时显示错误并退出；已有实例会被呼出，新进程退出。没有托盘、开机启动、自动更新或网络服务。

缓存写入系统 LocalAppData 已知目录的 `PicoRun\apps-v1.bin`。缓存包含原始 UTF-16 入口路径、名称和预计算搜索键，带版本、长度限制和校验，临时文件同步后用原生替换操作保存。损坏时重新扫描；读取失败不会将已有索引替换为空。每次启动仍重新发现应用，尚未实现先显示缓存、再异步刷新。

系统来源是用户/公共 Programs 和 Desktop 已知目录，支持重定向路径。目录扫描不跟随 junction/symlink，限制递归深度；同一路径去重，同名不同入口保留。F5 会重新读取系统目录位置。接受 `.exe` 与目标为 `.exe` 的 `.lnk`，不纳入文档、目录、网页快捷方式；Store/UWP、advertised/MSI 无普通 exe 路径的快捷方式暂不支持。

启动通过 ShellExecuteExW 传入原始入口，参数/工作目录不覆盖。采用 `SEE_MASK_NOASYNC | SEE_MASK_FLAG_NO_UI`，由窗口显示失败信息；系统安全提示仍可出现。这一调整没有降低下面观察到的 Shell 内存峰值。[微软接口说明](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-shellexecuteinfow)

## 验收

最终源代码通过 `cargo test --offline`（10 项测试）、`cargo fmt --check`、`cargo clippy --offline --all-targets -- -D warnings`、`cargo build --release --offline` 和 `git diff --check`。

单元/集成测试覆盖字典完整性、全拼/首字母/中文/简繁/中英混合/未知 Unicode、排名优先级与同分稳定性、前 12 项上限、空结果、删除/粘贴后的控制器、刷新失败保留索引、部分目录失败保留入口，以及缓存往返、替换、截断和校验损坏。

原生探针直接运行最终 release 启动器。500 个可控应用快捷方式和一个应被过滤的文档快捷方式存放在忽略目录；测试程序只记录参数与工作目录后退出。没有打开用户应用。已通过：

- 实际 Edit 的 Delete；WM_COPY/WM_PASTE；粘贴后立即 Enter 使用当前文本。
- Down/Down/Up 的结果选择；无匹配时 Enter 不启动进程。
- 中文查询与全拼/首字母；注入 IME 组合消息期间 Enter 不启动，结束后能打开预期入口。
- 中文/空格入口与 exe 路径、带空格参数及指定工作目录，验证 `.lnk` 语义保留。
- 入口删除后的可见错误、F5 删除失效项及重新发现恢复的入口。
- 第二实例退出并呼出已有窗口；实际键盘 Ctrl+Alt+F11 呼出/隐藏。
- 热键重复注册失败、占用时显示错误弹窗并退出、正常退出后可再次注册。
- 失焦隐藏消息、WM_CLOSE 正常退出、缓存损坏后重新发现并保存。
- 1000 次连续查询后的内存和 GDI/USER 句柄观察。

跨进程 Edit 测试使用可封送的 WM_SETTEXT/WM_GETTEXT；便利的 GetWindowText/SetWindowText 无法用于另一个进程的控件文本。启动器本身在窗口线程读取 Edit。[微软控件文本说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowtexta)

输入依赖原生 Edit 的 EN_CHANGE，刷新用投递消息合并，Enter 执行前同步实际文本。窗口回调不跨可能重入的控件/Shell 调用保留 Runtime 的可变借用；绘制使用独立快照与 Rc 资源所有者。窗口/控件销毁后释放字体与画刷，COM 引用、热键、互斥量按所有权释放。[EN_CHANGE 通知](https://learn.microsoft.com/en-us/windows/win32/controls/en-change)

**尚需人工/实机验收：**真实微软拼音候选窗口的组合、选词与取消；实际 Ctrl+C/Ctrl+V 和右键菜单操作（已测其原生命令路径）；真实焦点切换（已测对应消息）；多显示器跨 DPI 切换（当前截图为 175%）；Windows 10、32 位、极低配与内存换页。注入 IME 通知不是完整真实输入法验收。

## 测量口径

机器：i7-11700K，8 核/16 逻辑处理器，32 GiB 物理内存；Windows 11 Enterprise 25H2 build 26200，x64。CPU 型号从系统注册表读取，内存由 GetPhysicallyInstalledSystemMemory 复核。最终 GUI 测量在当前交互桌面执行；此前沙箱结果另存，不能混合成同一组数据。

完整进程使用 GetProcessMemoryInfo 的 PrivateUsage、WorkingSetSize、PeakPagefileUsage、PeakWorkingSetSize；私有提交与含共享页的工作集分别报告，MiB = 1,048,576 字节。峰值是从进程创建以来的系统高水位，能捕获两次采样之间的瞬时峰值。测试程序和测量器的内存不计入启动器；这也不是全系统增量内存或最低配承诺。没有调用清空工作集 API。

每套 5 个独立启动器进程，每进程 20 次窗口预热、120 次六种查询循环。首次删除应用缓存；第二次人为损坏缓存测试恢复；另外三次缓存有效。没有清空操作系统文件缓存，不能称为磁盘冷启动。所有启动均重新发现入口。

GUI 内存状态值取 5 个进程的中位数，括号为最小–最大。真实索引 394 项只做查询，不执行 Enter 启动用户应用。500 项套件另含可控 Shell 启动、IME 通知、错误恢复和压力操作，额外阶段单独列出。

500 项第一进程的首次 Shell 启动后：当前私有提交 8.85 MiB、工作集 40.19 MiB，已观察到峰值私有提交 44.28 MiB、工作集 78.91 MiB。所有可控启动、注入 IME、恢复与压力操作完成后的最大峰值为 **45.77 MiB 私有提交 / 81.10 MiB 工作集**，当前私有提交约 12.33 MiB。阶段采样能定位到首次 Shell 调用，尚不能归因到某个 Windows 组件或具体分配；不应把此成本省略或只报告搜索前的隐藏状态。

追加 1000 次窗口查询时，私有提交从 12.41 降至 12.33 MiB，工作集从 45.60 至 45.68 MiB，GDI 句柄保持 18，USER 句柄从 26 至 24。这一有限样本没有显示明显持续增长，不等于证明所有路径均无泄漏。

先等待 1 秒让窗口/输入任务完成，再测每进程 5 秒隐藏空闲。最终两套共 10 个区间，GetProcessTimes 的 CPU 时间增量均记为 0；较早运行曾观察到一个 15.625 ms 增量，不能承诺绝对零 CPU。程序使用 GetMessage 阻塞循环，没有应用定时器、周期扫描或轮询线程。

暂保留隐藏窗口，避免重复初始化原生控件；没有完成销毁/重建窗口的对照实验。**暂不加图标**，因为启动后的驻留和峰值尚需优化，几百 KiB 搜索索引并非最大已知成本。下一步优先拆分首次 Shell 调用的分配、系统组件与持久占用，再做 Windows 10 低内存实机验证。

## 原生窗口计时

外部探针同步发送控件文本消息、同步查询通知及 WM_PAINT，计时含跨进程消息往返、Edit 同步、搜索、动态布局和 GDI 绘制提交。它排除了物理键盘、真实 IME 候选交互和桌面合成器最终显示，**不是完整按键到屏幕延迟**。跨进程启动到探针发现窗口/Edit 的时间以 5 ms 间隔观察，含启动扫描，存在观察粒度。

| 套件 | 启动观察 P50/P95 ms，n=5 | 首次呼出+绘制 P50/P95 ms，n=5 | 每进程输入 P50/P95 的中位数 ms，5×120 |
| --- | ---: | ---: | ---: |
| 500 项可控入口 | 315.57 / 394.81 | 46.72 / 64.52 | 4.42 / 9.76 |
| 394 项真实索引 | 418.31 / 490.61 | 23.36 / 30.26 | 5.27 / 7.28 |

输入 P95 在各轮的范围：500 项 3.12–10.16 ms，真实索引 6.23–9.09 ms；n=5 的跨进程 P95 按 nearest-rank 等于最大值，样本很少。启动扫描同步进行，仍有改进空间。

## 纯搜索与索引

另运行 5 个独立 search_bench 进程，固定在可用的首个逻辑 CPU（本机逻辑 CPU 0）。每组 500/2000/10000 项，由五种标题加序号构成；12 种固定输入含空串、中文、全拼、首字母、中英混合和无匹配。每组先 20 轮×12 种预热，再 100 轮×12 种计时（每进程每组 1200，跨进程每组 6000）。Instant 只包围 search 调用，nearest-rank P95；下面对各进程 P50/P95 再取中位数，不是合并样本的百分位。

| 项数 | 搜索 P50 ms | 搜索 P95 ms | 各轮 P95 范围 ms | 索引构建中位数 ms | 自有堆容量字节 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 500 | 0.0232 | 0.0558 | 0.0414–0.0572 | 0.7413 | 121,074 |
| 2000 | 0.0951 | 0.1996 | 0.1957–0.2372 | 2.3046 | 488,874 |
| 10000 | 0.5655 | 1.5427 | 1.2371–1.5990 | 11.9652 | 2,461,674 |

预热前每组首次 `weixin` 搜索的中位数为 25.8 / 125.6 / 614.5 µs，只有每进程一次，不能形成可靠冷态 P95。索引构建含标题/路径分配与拼音预计算，不含磁盘发现；后两组字典页已由前组访问。

自有堆容量按 Vec/String/PathBuf 实际容量加条目数组统计，不含 allocator 元数据、字典只读页、Shell/GUI/系统组件。搜索基准本身在 10000 项索引点的私有提交约 4.32–4.34 MiB，工作集约 8.55–8.56 MiB；它不是完整启动器。先前受竞争影响的探索样本也保留，最终五次运行不与 GUI 探针并行。

## 重现与证据

```powershell
cargo test --offline
cargo fmt --check
cargo clippy --offline --all-targets -- -D warnings
cargo build --release --offline
Start-Process .\target\release\native_probe.exe -WindowStyle Hidden -Wait
Start-Process .\target\release\native_probe.exe -ArgumentList '--real' -WindowStyle Hidden -Wait
.\target\release\search_bench.exe
```

探针真实热键测试需要当前交互桌面；沙箱中实际键盘注入未触发，当前桌面复测通过。运行探针前退出已有 PicoRun，临时 Ctrl+Alt+F11 必须可用。真实套件不会打开用户应用。失败时查看 `runtime/probe-error.txt`。

本机原始证据在 `.gitignore` 覆盖的 `runtime/`：`metadata.json`、`probe-controlled/{memory.csv,timings.txt,checks.txt,window.bmp}`、`probe-real/{memory.csv,timings.txt,checks.txt}`、`search-bench-final-1.txt` 至 `5.txt`；早期沙箱/旧 Shell 调用样本另存。真实入口缓存和测试快捷方式也只在忽略目录，不提交个人清单或路径。

整体发布许可证仍待用户决定；只保留既有拼音数据 MIT 许可与来源说明。上述结果不继承旧核心性能、不证明 Windows 10 或 32 位兼容，也不证明极低配机器达到同样响应。
