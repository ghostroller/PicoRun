# 应用结果图标成本评估

2026-10-03：用独立可运行原型评估图标，正式 `src/` 和 `target/release/picorun.exe` 没有加入此功能。结论是：**可以作为可关闭的增强选项，优先采用后台直接提取资源；针对最低内存目标，建议默认关闭。** 常驻和查询响应的增量较小，但提取图标的 CPU 工作量与瞬时内存峰值仍需重视。

随后已按用户要求完成独立原型的缓存优化与同场对照，见 [ICON_CACHE_RESULTS.md](ICON_CACHE_RESULTS.md)。真实样本活动 CPU 中位数减少 14.2%，查询绘制中位数减少 15.0%；常驻变化很小，提取峰值仍未解决。下文保留优化前基线和研究过程。

## 实测结论

本机 394 个真实应用入口，直接提取方案与无图标各 5 个独立进程。下表常驻取连续查询后的组中位数；时间取每进程 P50 的中位数；峰值取各组最终累计峰值的最大值。差值为两组统计量之差。

| 指标 | 无图标 | 后台直接提取 | 增量 |
| --- | ---: | ---: | ---: |
| 完整进程私有提交 | 4.67 MiB | 5.82 MiB | +1.15 MiB，约 25% |
| 完整进程工作集 | 28.07 MiB | 30.44 MiB | +2.37 MiB，约 8% |
| 新结果查询与首次绘制 | 6.44 ms | 6.89 ms | +0.45 ms，约 7% |
| 缓存命中的同一查询 | 3.79 ms | 3.71 ms | 波动范围内，没有速度提升结论 |
| 缓存图标下完整 12 行 GDI 绘制 | 2.29 ms | 2.90 ms | +0.61 ms，约 27% |
| 本轮整个活动负载累计 CPU 时间 | 5.97 s | 11.63 s | +5.66 s，约 95% |
| 累计私有提交峰值最大值 | 4.68 MiB | 14.77 MiB | +10.09 MiB |
| 累计工作集峰值最大值 | 28.14 MiB | 38.85 MiB | +10.71 MiB |

27% 是完整列表的绘制阶段增量，7% 是本机查询探针中位数的差值；都不能解释为整个产品统一降低这个百分比。查询的五轮 P50 差值为 +0.66、+0.51、+0.45、−1.09、+0.44 ms，存在调度和前台状态波动，没有统计显著性检验。CPU 时间是整个进程在同一活动负载期间使用的处理器时间之和，包含主线程和后台线程；该负载包含绘制基准、200 次不同查询、缓存查询和 1000 次快速轮换，不能换算为普通使用的持续 CPU 占用率。

直接方案第一次呼出时，文字先出现，全部首屏图标就绪的 P50/P95 为 **128.30 / 162.50 ms**。后续换到新的结果集合，文字绘制 P50/P95 为 **6.89 / 11.54 ms**，当前结果图标全部就绪为 **10.83 / 37.87 ms**。图标提取异步进行，用户无需等全部图标完成才能继续查询。

对于本机普通使用，上述响应和常驻成本可以接受。对于勉强运行 Windows 10 的机器，在换页或慢磁盘下，额外峰值和后台提取工作可能更明显；此环境尚未实测，不能承诺可接受。若正式实现，建议沿用托盘勾选开关，不必为一个选项单独增加设置窗口。

## 两条提取路径

两种方案都只请求当前最多 12 个可见结果，使用懒创建的一个 STA 工作线程、48 条 LRU 缓存、最新请求替换、代次检查和容量为 1 的完成队列。空闲通过条件变量阻塞，不设周期轮询；主线程使用已有 HICON 绘制，不同步提取。缓存持有最多 48 条记录，包含失败/通用图标；当前显示快照和待消费结果还持有少量引用，整个进程的 HICON 数量并非严格只有 48。

- **Shell 路径**：`SHGetFileInfoW(SHGFI_ICON)`，直接请求原始入口的 Shell 图标。微软要求将此调用放在后台，因为 UI 线程调用可能导致界面无响应；返回图标需要释放，调用线程需要初始化 COM。[SHGetFileInfoW 文档](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shgetfileinfow)
- **直接资源路径**：对于 `.lnk`，用 `IShellLinkW::GetIconLocation` 读取快捷方式指定的图标文件与索引；没有指定时读取其目标路径。展开环境变量后，使用 `ExtractIconExW` 读取 exe/dll/ico 资源，保留负资源 ID。提取失败则复制系统通用应用图标，不额外调用 Shell 回退。[GetIconLocation 文档](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishelllinkw-geticonlocation)、[ExtractIconExW 文档](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-extracticonexw)

直接路径在工作线程复用两个 32,768 个 UTF-16 单元的缓冲，总计 128 KiB，避免每次提取重新分配大缓冲。HICON 由引用计数对象持有，最后一个引用释放时 `DestroyIcon`；renderer 在调用 `DrawIconEx` 期间保持显示快照存活，没有 Runtime 可变借用跨可能重入的 Win32 调用。[DrawIconEx 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-drawiconex)

这条轻量路径不完整复制 Explorer 的 Shell 图标处理和覆盖标记。真实样本的前 200 次查询共触发 224 次提取，其中 14 次使用通用图标，可能包括目标没有资源等情况；首屏 12 个真实图标均有资源。合成样本包含一个 `%SystemRoot%\System32\shell32.dll,-154` 的快捷方式自定义图标，截图确认环境变量与负资源 ID 正确生效。其余合成目标没有自有图标，使用通用图标，不能代表 500 个各不相同的真实应用图标。

## 后续缓存优化空间

同日追加只读分析：读取本次真实索引缓存，再通过 WScript.Shell 读取已有快捷方式的 IconLocation/TargetPath，展开环境变量，按图标资源路径（忽略大小写）和索引分组；没有 Save、提取图标或启动应用。394 个入口全部解析成功，得到 **293 组资源描述，101 个重复描述（约 26%）**；前 200 个入口对应 148 组描述，单个描述最多被 5 个入口使用。293 条唯一资源路径字符数据合计 29,312 字节（UTF-16 口径），不包含结构体、入口映射、文件校验和分配器开销。此处是资源描述去重，不是像素内容比较，也不是优化后的性能测量。

当前实验 LRU 以原始入口路径作为键，容量 48；缓存未命中时重新解析 `.lnk`、展开资源路径、提取图标。五轮真实压力负载结束时，后台缓存累计查找命中率为 8.00–8.20%。这主要反映前 200 个入口轮换超过缓存容量；同一结果集合的重复查询被 Session 跳过，不计入这些后台查找，不能将这个比例当作日常用户查询命中率。

| 优先级 | 优化 | 预期作用与边界 |
| --- | --- | --- |
| 先做 | 缓存入口到图标资源的解析结果，与少量 HICON 缓存分开 | HICON 被淘汰后仍不必重新读取快捷方式；元数据按字节限制，启动/手动刷新时校验，不加载全索引像素 |
| 先做 | HICON 按资源路径、索引、尺寸/DPI 共享；通用图标共享单个实例 | 同资源的多个入口复用，负结果按资源缓存；保持缓存有界，保留快捷方式自定义图标索引，F5/资源变更/DPI 变化需要失效处理 |
| 之后实测 | 有界持久化图标像素缓存，后台仅读取可见项 | 有机会减少重启及淘汰后的资源提取；需版本、损坏恢复和资源变化校验。磁盘缓存不应全量载入内存，不能承诺直接消除本次约 10 MiB 的峰值增量 |

优先减少重复解析和资源提取，容量根据内存预算和命中率调整。单纯将 HICON 缓存从 48 加大，在上述轮换负载中仍可能淘汰，且增加资源驻留。缓存主要改善加载阶段；已有图标的约 0.61 ms 绘制增量还需要单独研究尺寸匹配和 renderer。去重描述减少约 26%，实际 CPU、常驻和峰值收益需要新的同场对照，没有已实现或已达到的优化比例。

## 环境与测量口径

i7-11700K（8 核/16 线程）、32 GiB、Windows 11 Enterprise 25H2 build 26200 x64；Rust 1.95.0 MSVC，release opt-level=3、fat LTO、codegen-units=1、panic=abort、strip、静态 CRT、离线构建。没有新增 Rust crate、Web UI 或产品运行时脚本依赖。图标在 renderer 中按 20 个逻辑像素绘制，本次只测本机当前缩放。

最终四组共 **32 个独立进程**：每条提取路径的真实样本各 5 轮开启/关闭、合成样本各 3 轮开启/关闭；奇偶轮交替先测关闭/开启，避免固定顺序偏差。每个进程均正常退出，驱动确认窗口可见、查询确实同步、缓存不超过 48 条；没有打开任何索引应用。

1. 新进程隐藏启动；首次使用单独的测试数据目录，后续复用应用缓存，每次仍发现入口。等待 100 ms 后采集隐藏状态。
2. 首次呼出并绘制文字；等后台首屏请求完成并绘制，记录就绪时间；再等 100 ms 采集显示状态。图标进程内缓存为空，没有清空 Windows 文件缓存，**不是磁盘冷启动**。
3. 同一 12 行列表预热 20 次，外部探针测 200 次绘制。另用 UI 线程内部计时预热 20 次、测 200 次完整 GDI 绘制，单独报告内部绘制成本以排除消息 IPC 时间。
4. 依次查询前 200 个索引入口的名称，每次同步 Edit、查询和绘制，再等本次图标完成。名称由被测进程内部解析，不将个人名称或路径写入结果。
5. 同一缓存命中查询预热 20 次、计时 120 次；接着 1000 次快速轮换前 200 个查询，只等最后一代图标完成。过期请求合并，提取次数不必等于 1000。
6. 显式隐藏，等待 500 ms 后记录 2 秒空闲 CPU，正常关闭。驱动等待图标时的 1 ms 轮询只发生在测试脚本，不属于被测应用。

测试目录启用自身英文输入选项，避免将本机小狼毫组合输入的组件成本混入图标对照。查询是跨进程消息同步设置 Edit 后真实执行查询/绘制，含驱动与 IPC 成本；没有物理键盘输入，不等于按键到屏幕显示延迟。为稳定采样，原型使用独立窗口类/单实例名，关闭焦点丢失自动隐藏、物理 Edit 快捷键和全局热键注册，改用诊断消息控制隐藏；这些只用于实验，不能视作正式图标与 IME、热键、窗口行为的完整验收。

完整进程采样使用 PrivateUsage、WorkingSetSize、PeakPagefileUsage、PeakWorkingSetSize 和进程 CPU 时间，包括已加载的系统组件；排除测量器、Explorer、外部输入法服务和其他进程，不是整个系统的增量。没有清空工作集。峰值是操作系统维护的进程累计峰值，取到最后一次采样，包含扫描、显示、取图和持续查询，没有应用启动。

内存 P50/P95 使用独立进程间最近秩；n=5 或 n=3 时 P95 就是最大值。重复查询/绘制先算各进程的 P50/P95，再取进程间中位数；首次启动/呼出只有每进程一条样本，直接在独立进程间取 P50/P95。少量进程不能预测低配机器的尾延迟。
